### 添削
**解説あり（AC版）**
1. `if (i + m - 1 > n) break;` は境界が1つ緩い。
   - 正しい条件は「`i + m > n` なら末尾まで届かない」。
   - `i + m - 1 == n` のときも `substr(i, m)` は長さが足りない文字列を返す。そのため `== t` が false になり、結果は偶然合っている。
   - 意図を明確にするには次のように直す。
   ```cpp
   -        if (i + m - 1 > n) break;
   -        if (s.substr(i, m) == t) {
   -            A[i] = 1;
   -        }
   +        if (i + m > n) break;
   +        A[i] = (s.compare(i, m, t) == 0);
   ```
   `compare(pos, len, str)` なら部分文字列を作らず、そのまま比較できる。ただし m ≤ 10 なので、`substr` でも小文字列最適化によりヒープ確保は起きず、速度の差はほぼない。
2. 判定部分は1行にできる。`if (r - l + 1 < m) yes_no(false); else ...` は次のように書き換えられる。
   ```cpp
   yes_no(r - l + 1 >= m && sums[r - m + 1] - sums[l - 1] > 0);
   ```
   `&&` が短絡評価されるので、`r - m + 1 < l` のときに `sums` を読むこともない。
3. オーバーフローはない。`sums` の最大値は |S| ≤ 4×10^5 なので `int` で足りる。
4. `sums[r - m + 1] - sums[l - 1]` が「0-indexed の開始位置 l-1 〜 r-m の個数」になる式は正しい。あとで読み返せるよう、`// 開始位置 [l-1, r-m] の出現数` のようなコメントを1行足すとよい。

**自力(tle)版**
1. `substr` でクエリごとに最大 |S| 文字をコピーしており、これだけで O(Q·|S|) かかる。
   - `string_view` にすればコピーは消える。
   - それでも `boyer_moore_searcher` の探索自体が範囲長に比例するため、最悪ケースの O(Q·|S|) は変わらない。
2. |T| ≤ 10 という制約を使っていない。ここが方針の分かれ目になる。
   - 範囲ごとに検索するのではなく、「T が S のどこから始まるか」を先に1回だけ求めておく。
3. `boyer_moore_searcher` は長い T や大きな文字種で効く道具。|T| ≤ 10 ではほとんど効かないので、この問題には向かない。

### 解説
- **着眼点**
  - T は最大10文字しかないので、S 全体で「T がどこから始まるか」を `O(|S|·|T|)` で全部調べられる。
  - クエリ [L, R] に T が含まれるのは、T の開始位置 i が L ≤ i ≤ R−|T|+1 に1つでもあるとき。
  - つまり「T が含まれる」を「区間内に開始位置が1つ以上ある」に言い換えられる。
- **想定解**
  - 開始位置に 1 を立てた 0/1 配列を作り、累積和を取る。
  - 各クエリは `R−L+1 < |T|` なら No。そうでなければ区間 [L, R−|T|+1] の和が 0 より大きいかを見る。
  - 計算量は前処理 O(|S|·|T|) + クエリ O(Q)、メモリ O(|S|)。
- **本人の解法との比較**
  - AC 版はこの想定解と同じ。
  - TLE 版との違いは、「クエリごとに文字列を探す」のをやめて「S 全体で1回だけ探して、クエリは累積和で答える」に変えた点。
  - 全体で1回の前処理にまとめると、クエリごとの計算が定数時間になる。
- **別解**
  - T が10文字以下なので、ローリングハッシュや Z-algorithm は不要。
  - |T| が大きい制約なら、KMP で開始位置を O(|S|+|T|) で求め、同じく累積和にすればよい。
