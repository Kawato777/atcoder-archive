### 判定
どちらも **RE の原因は同じ**: 制約が `1 ≤ H, W ≤ 10^9`（メモリ 1024 MiB）なのに、`H`・`W` の大きさの配列を確保していること。
- 解説あり: `vector<int> A(h), B(w)`
- 自力: `vector<int> c(h), d(w), e(h + 1), f(w + 1)`

`int` 1 つ 4 バイトなので、`h = 10^9` なら 1 本で約 4 GB になります。確保に失敗して `std::bad_alloc` で異常終了し、AtCoder 上では RE（環境によっては MLE）になります。手元で `h = w = 10^9` を入力して `vector<int>(h)` を確保すると `std::bad_alloc` で abort することを確認しました。サンプルは `H, W` が小さいので通ります。「途中で RE」は、`H, W` が大きいテストケースで落ちているためです。

「解説あり」のコードには、これとは別に 2 つ問題があります。
- `A(h)`・`B(w)` に `i < n` で書き込んでいる（`n > h` や `n > w` だと範囲外書き込みになる）。ただし `H, W` が大きいケースでは先に確保で落ちます。
- `count_if` が毎クエリ全要素を走査するので O(NQ) で、`3×10^5` 同士なら TLE。

修正版（「解説あり+claude」）は、サンプル 1 の出力 `3 3 0 5 2 1` が期待通りになることを確認済みで、上の 2 点とも解消されています。

### 添削
1. **配列サイズが `h`・`w`（致命的）**: サイズは `h`・`w` ではなく `n` にします。クエリは「行・列の位置が `[k, l]` に入る駒の個数」を聞いているだけなので、駒の座標 `N` 個だけ持てば足ります。
   ```diff
   -    vector<int> A(h, 0), B(w, 0);
   +    vector<int> A(n), B(n);
   ```
2. **`count_if` による線形走査（TLE）**: ソート済みなので、二分探索で個数を求めます。
   ```diff
   -        cout << count_if(A.begin(), A.end(), [&k, &l](int m) { return m >= k && m <= l; }) << "\n";
   +        cout << upper_bound(A.begin(), A.end(), l) - lower_bound(A.begin(), A.end(), k) << "\n";
   ```
   `B` も同様にします。`j` で `A` と `B` を選ぶ部分は `auto& v = (j == 1 ? A : B);` にまとめると、分岐が 1 つで済みます。
3. **自力解法**: 「個数を数えて累積和」という方針は正しいです。ただ、累積和の配列を座標で直接引くので、サイズが `H`・`W` になってしまいます。これを座標圧縮に置き換えるのは、二分探索版と同じ発想になります。
4. **入出力**: 自力版の `endl` は 3×10^5 回でもギリギリ通りますが、`"\n"` にして `ios::sync_with_stdio(false); cin.tie(nullptr);` も付けておくと安全です。

### 解説
- **着眼点**: `H, W` は 10^9 ですが、駒は高々 `N ≤ 3×10^5` 個です。行と列は独立に数えればよく、駒のある座標だけを見れば足ります。
- **想定解**: 行番号の配列 `R` と列番号の配列 `C` を別々にソートします。クエリ `1 u d` は `R` 中の `[u, d]` に入る要素数、`2 l r` は `C` 中の `[l, r]` に入る要素数で、`upper_bound(d) - lower_bound(u)` で求まります。前処理が O(N log N)、各クエリが O(log N) で、全体は O((N+Q) log N)。
- **本人の解法との比較**: 「解説あり」は発想（行と列を別々にソートして数える）は同じですが、数え方が O(N) なので TLE になります。自力は累積和で O(1) にできる点は良く、座標が大きいだけなのが惜しいところです。制約を先に見て、「配列のサイズに使えるのは `N`・`Q` 側の値で、10^9 の `H, W` は使えない」と判断するのが肝です。
- **別解**: 座標圧縮して累積和にする方法もありますが、二分探索のほうが短く書けます。

### 学んだこと
- [Qiita: std::count_if](https://qiita.com/HnniTns/items/1a6a6f05bdcefdd4a786): 条件を満たす要素数を数える関数で、計算量は要素数に比例する O(n) です。「解説あり」の `count_if(...)` の行がこれです。この問題では、O(n) の関数を毎クエリ呼ぶことが TLE の原因になります。
- [morinokabu: count / count_if](https://morinokabu.com/2025/09/01/cpp-count-elements-in-container-count-count-if/): ページ本文を取得できなかったので、内容には触れません。
- [note: C++ のラムダ式](https://note.com/a_____aaaaaa/n/nb5cc6be23c9b): ABC482 C の解説ではなく、ラムダ式の一般的な紹介記事です。キャプチャ（`[&]` は参照、`[=]` はコピー）の話が、`count_if` に渡している `[&k, &l](int m){...}` に対応します。ただし、これは RE・TLE の原因ではありません。
- [Qiita: lower_boundとupper_boundの使い方](https://qiita.com/ganyariya/items/33f1326154b85db465c3): `lower_bound` はキー以上の最初の要素、`upper_bound` はキーより大きい最初の要素へのイテレータを返し、どちらもソート済みの範囲が前提です。`upper_bound - lower_bound` は同じキーが何回出てくるかを表すので、これを `[k, l]` の範囲に広げたのが「修正版」の `upper_bound(l) - lower_bound(k)` です（`lower_bound` は `k` 以上の最初の位置、`upper_bound` は `l` より大きい最初の位置）。該当する要素がなければ、どちらも末尾（end）の位置を返すので、範囲外のクエリでも 0 が返ります。`binary_search` は bool しか返さず、位置や個数が分からないため、この問題では使えません。なお、この記事に計算量の記載はありません。O(log n) というのは一般的な二分探索の性質です。
