### 添削
**1. `main.cpp` の指摘（優先度順）**

(a) 計算量（`reduce` の区間が長い）
- `2 y` のたびに `reduce(cnt.begin() + k + d, cnt.end())` で、値ごとの個数を最大値まで足し直している。1 クエリのコストは `cnt` の長さに比例する。
- 他のマスが 0 のまま、1 マスだけに積み続けると、`d` は増えず `cnt` の長さが Q 近くまで伸びる。そこで `y` が小さいクエリを大量に投げると O(Q²) になる。
- 手元の測定（N=2、`1 1` を a 回、続けて `2 1` を 30 万 − a 回）では、a=5000 で 0.20 秒、a=20000 で 0.90 秒、a=50000 で 1.77 秒、a=15 万で 3.7 秒だった。
- AC したのは、`vector` の連続メモリを足すだけで定数倍が小さく、SIMD 化もされるため。

(b) 符号なし整数との比較
- `cnt.size() - 1 < L[k - 1]` と `cnt.size() < k + d` は、`size_t` と `int` の比較になる。
- 今回は値が常に 0 以上なので結果は正しいが、`-Wsign-compare` の警告が出る。`(int)cnt.size()` にキャストするとよい。

(c) `push_back` の分岐を簡単にできる
- `L[k - 1]++` のあと、`L[k - 1]` は `cnt.size()` 以下にしかならない。だから次のように書ける。
- なお、`cnt[d] <= 0` の判定は、1 回の操作で最小値が高々 1 しか増えないので、`d++` が 1 回で足りるという前提で正しい。

```diff
-            if (cnt.size() - 1 < L[k - 1]) {
-                cnt.push_back(1);
-            } else {
-                cnt[L[k - 1]]++;
-            }
+            if ((int)cnt.size() <= L[k - 1]) cnt.push_back(0);
+            cnt[L[k - 1]]++;
```

(d) オーバーフロー
- 指摘なし。ブロック数は高々 Q、個数は高々 N、`k + d` は 6×10^5 以下なので、`int` で足りる。

**2. 修正方針（`main.cpp` に対する差分）**

```diff

-    cnt.push_back(n);
+    vector<int> L(n, 0), ge(q + 2, 0);  // ge[v] = 保存値が v 以上のマスの数（v >= 1）

         cin >> j >> k;

-            cnt[L[k - 1]]--;
-            L[k - 1]++;
-            if (cnt.size() - 1 < L[k - 1]) {

-            } else {

-            }

-            if (cnt.size() < k + d)
-                cout << 0 << "\n";
-            else
-                cout << reduce(cnt.begin() + k + d, cnt.end()) << "\n";
```

- 修正版は愚直解と 1500 件一致した。最悪ケース（上の例）でも 0.08 秒だった。
- `y` は Q と無関係に最大 3×10^5 まで取れる。そのため、`k + d < ge.size()` の範囲チェックは必須。

**3. `map` 版が TLE になった原因**
- `main.cpp` と同じく、`2 y` のたびに値ごとの個数を足し直している。計算量は同じ O(Q·M)。
- 差が出たのは**定数倍**。`map` は 1 要素ごとに O(log) の木の探索とポインタ追跡が必要で、`vector` の約 100 倍遅くなる。
- 手元では、`1 1` を 5000 回、続けて `2 1` を約 29.5 万回の入力で、`map` 版は 30 秒で打ち切りになった。同じ入力で `vector` 版は 0.2 秒だった。
- さらに `cnt[L]--` で 0 になったキーを消さないので、`cnt.size()` は減らない。上限 `cnt.size() - 1` が「最大値」と一致しているのは、キーが一度も消えず連続しているからで、偶然に近い。
- ループ内の `cnt[l]` は、存在しないキーを新規に挿入する。今回は起きないが、キーを消す修正を入れた途端に壊れる。

### 解説
- **着眼点**
  - 「全マスから 1 個ずつ取り除く」操作は、全マスを書き換えずに全体の引き算の回数 `d` だけを持てば表せる（実際の値 = 保存値 − d）。
  - 「y 個以上のマスの数」は、毎回数えるのではなく、更新時の差分で保つ。
  - 1 回の操作で増えるのは 1 マスだけ。保存値が `v−1 → v` になるとき、「v 以上」の数が 1 増えるのは `ge[v]` だけ。
  - 全マスに 1 個以上ある条件は `ge[d+1] == n` で判定できる。`d` は 1 回の操作で高々 1 しか増えない。
- **想定解**: O(N + Q)。1 クエリあたり O(1)。
- **本人の解法との比較**
  - 発想（全体オフセット `d` と保存値、値ごとの個数表）は想定解と同じで、AC もしている。
  - 違うのは、答えを「個数表の区間和」で毎回求めるか、「v 以上の個数」を更新時に保つかの 1 点。
  - 前者は定数倍が小さい `vector` なら通ったが、`map` では TLE になった。
- **別解**: BIT（Fenwick tree）で個数表の区間和を取る方法（O((N + Q) log Q)）。今回は更新が +1 の 1 点だけなので、`ge` で足りる。
