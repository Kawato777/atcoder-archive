# AtCoder 解答の添削・解説・タグ付け（リポジトリ版）

対象: このリポジトリ（C++23 / GCC 15、`scripts/test` と同じ `-std=gnu++23 -O2`）

**ファイルには一切書き込まない**（Edit / Write / git は使わない）。結果は最終出力にだけ出し、取り込みは本人が
VS Code 拡張または `scripts/note --apply` で行う。

VS Code 拡張の「🤖 Claude で添削」から `claude -p` で起動されることを想定している。その場合は質問しても
答えが返らないので、確認が必要な場面では **取り込み用ブロックを出さずに** 理由を書いて終える（拡張がエラーとして表示する）。

## 入力
- 解答ファイルのパス（リポジトリ相対）。次のどれか
  - `practice/<種類>/<番号>/<問題>/main.cpp`（または問題のディレクトリ）
  - `contest/<種類>/<番号>/<問題>.cpp`（参加した回。ノートは `practice/<種類>/<番号>/<問題>/note.md`）
- 問題URLは `main.cpp` の1行目のコメントにある。無ければ `./scripts/note --info <パス>` の note の場所や、
  ディレクトリ名（`practice/ABC/484/C` → `https://atcoder.jp/contests/abc484/tasks/abc484_c`）から決める。
  決められなければ、その旨を書いて終える。

## 0. 開始前チェック（必須）
- コンテストが **開催中** なら何もせず断る。AtCoder生成AI対策ルールは ABC / ARC / AGC の開催中に適用され、
  過去問の練習には適用されない。
  - 指示文に「コンテスト終了はユーザー確認済み」とあれば、それに従う
  - それ以外で開催中かもしれない（直近の回など）場合は、コンテストページ（`https://atcoder.jp/contests/<id>`）で
    終了時刻を確認する。確認できなければ断る
- コードの一部が欠けている（`main` が無い等）なら、何が足りないかを伝えて終える。

## 1. 情報収集
1. 問題文を WebFetch で取得する（制約・入出力・サンプルを把握）。`?lang=ja` 付きのURLも試す。
   取れない場合は WebSearch で問題名を確認する。
2. 必要なら公式解説 `https://atcoder.jp/contests/<id>/editorial` を参照する。問題文や解説の文章はそのまま貼らず、
   自分の言葉で説明する（公開リポジトリに載るため）。
3. リポジトリを読む（Read / Glob / Grep）:
   - 対象のソースと、あれば `note.md`（`./scripts/note --info <パス>` で場所が分かる）
   - `./scripts/note --history` で全ノートの `{path, url, status, tags}` を得る（「過去ノートとの照合」に使う）
4. 検証: `./scripts/test <ソースのパス>` でサンプルを実行する（ビルドとサンプル判定をまとめて行う）。
   - `contest/` の解答は、隣に `test/` が無ければ `practice/<種類>/<番号>/<問題>/test` のサンプルが使われる
   - どちらにも `test/` が無いと失敗する。その場合は「サンプル未取得のため未実行」と書く（取得はしない）
   - ファイルを作れないので、愚直解とのランダム比較は行わない。怪しい入力は手で追って反例を示す

## 2. 出力
日本語で、簡潔かつ技術的に正確に書く。最終出力は **取り込み用ブロック1つだけ** にする（前後に説明文を入れない）。
中身は次の4節。

### 判定
- 正しいと思うか、怪しい点があるかを1〜2行で。`scripts/test` の結果（AC 数 / 全体）も書く。

### 添削
優先度の高い順に、該当行を示して具体的に指摘する。
- 正当性: WA になりうる入力（境界・N=1・全部同じ値・最大値など）。可能なら反例を具体的に示す
- オーバーフロー（`int` で足りるか、`long long` が必要か）
- 計算量: 制約に対して TLE しないか
- 実装: 無駄な処理、より簡潔な STL の使い方（`ranges`、`accumulate` 等）、可読性
- 修正は **差分の形で最小限** にする（```diff または ```cpp）。コード全体の書き直しはしない（コードは本人が書く方針）
- 問題が無ければ「指摘なし」と書き、無理に指摘を作らない

### 解説
- **着眼点**: 何に気づけば解けるか
- **想定解**: 方針と計算量
- **本人の解法との比較**: 同じか。違うならどちらが良いか
- 別解があれば短く

### 過去ノートとの照合
`./scripts/note --history` の結果を使い、この問題で使う典型・手法が過去のノートに出てきたかを判定する（対象自身のノートは除く）。
- 一度も出てこない → 「記録上は初出」とし、`review: true` を勧める
- 出てきたことはあるが、その時の status が全て解説AC → 「未定着」とし、`review: true` を勧める
- 自力AC・本番AC で何度か出てきている → 「既習」とし、`false` でよい
- 同じタグの過去問があれば、パス（と URL）を挙げる
- タグ入りのノートが少なく判断材料が足りない場合は、そのまま「判断材料が足りない」と書く。断定しない
- 判定できるのは「記録に無い」ことだけで、本人が知らないかどうかは分からない

## 3. 取り込み用ブロック（形式）
`scripts/note --apply` がそのまま読める形式。中にコードブロックを含むので、外側のフェンスはバッククォート **4つ**（````）。

````markdown
---
tags: [DP, 二分探索]
time: O(N log N)
space: O(N)
review: true
---
## Claude による添削・解説（AI生成）
<!-- YYYY-MM-DD Claude が生成。AI 生成の節より上は本人が書いている -->
対象: [main.cpp](main.cpp)

### 判定
...

### 添削
...

### 解説
...

### 過去ノートとの照合
...
````

形式のルール:
- frontmatter には `tags` `time` `space` `review` の4つだけを入れる。`status` は入れない（本人が決める）
- 値に `#` `,`（tags の区切り以外） `[` `]` と「: 」は使わない（`scripts/note` が受け付けない）
- 見出しは対象で変える。`practice/` の解答は `## Claude による添削・解説（AI生成）`、`contest/` の解答（本番のコード）は
  `## Claude による添削・解説（AI生成・本番）`。`scripts/note --apply` は同じ見出しの節だけを置き換えるので、
  本番の添削は復習で practice/ を添削しても残る（復習の節は最新の1つだけ）
- 見出しと日付コメントの次の行に、添削したコードへの note.md からの相対リンクを `対象: [パス](相対パス)` の形で書く
  - `practice/ABC/484/A/main.cpp` → `対象: [main.cpp](main.cpp)`
  - `contest/ABC/484/A.cpp` → `対象: [contest/ABC/484/A.cpp](../../../../contest/ABC/484/A.cpp)`
- frontmatter の後は AI 生成の節（上の見出しのどちらか）だけ。本人が書く本文（着眼点／解法／ハマった点・学び）の下書きは入れない
- 節の中は `###` 以下の見出しだけを使う（`##` を使わない）
- 日付は実行日を入れる。問題文・公式解説の文章を引用しない

## 4. タグの選び方
[tags.md](tags.md) に従う。
